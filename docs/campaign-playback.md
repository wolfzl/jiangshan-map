# 新增「战役推演」操作手册

本文档写给接手新增战役的 AI 编码代理（Codex 等）和开发者。目标：**只加数据，不改渲染代码**，就能为一场战役做出分阶段、分敌我的进军推演。

现有范例：长平之战（`changping`）。动手前先打开 `http://127.0.0.1:8000/?year=-260&campaign=changping&cphase=1`，逐个阶段看一遍，你要做出的就是这种效果。

---

## 1. 功能是怎么工作的

- 所有代码和数据都在 [`js/atlas_campaigns.js`](../js/atlas_campaigns.js)，样式在 [`css/style.css`](../css/style.css) 末尾的 `Campaign playback` 段。
- 模块通过 `window.__ATLAS_MIXINS` 挂到 `HistoricalAtlasController` 上，并包装了 4 个已有方法：
  - `openMilestoneBalloon`：事件浮签里出现「⚔ 战役推演 ›」入口按钮；
  - `jumpToYear`：时间轴拖出战役年份范围就自动退出；
  - `_rescaleSvgTypography`：缩放后按屏幕像素重绘，保证线宽、字号不变；
  - `_urlStateParams`：把状态写进 URL（`?campaign=<key>&cphase=<从 1 开始的阶段号>`）。
- 进入推演后：隐藏原有的事件图钉和图例；放大到战术尺度（屏幕可见宽度小于约 4.6 个经度，即相机宽度 < 60 个 SVG 单位）时淡化地形、隐藏城名层；笔记本宽度下自动收起右侧编年栏。
- 每个阶段切换时：时间轴跳到该阶段的 `year`，相机飞到该阶段的 `view`，箭头按顺序「生长」出来。

**新增一场战役 = 在 `CAMPAIGNS` 对象里加一个条目（外加可能需要的 `P` 地点和 `PLACE_NAMES` 名称）。** 除非本文档第 7 节列出的情况，不要改渲染函数、CSS 或 `app.js`。

---

## 2. 工作流程

1. **考据**：先写出阶段大纲（时间、双方主将、兵力、每一步谁从哪里去了哪里、结果），注明史料出处（《史记》《三国志》《资治通鉴》等）。数字和人名有争议的，按通行说法并在 `source` 里写明「示意复原」。
2. **找挂载事件**：在 [`js/map_data.js`](../js/map_data.js) 里找到这场战役对应的编年事件（`milestones` 条目），记下所在朝代的 `key`、`year`，以及 `site` 字段里一个能唯一识别的子串。例：
   - 赤壁：朝代 `donghan`，`year: 208`，`site: "赤壁 · 江陵"`，可用 `site: '赤壁'`；
   - 淝水：朝代 `dongjin`，`year: 383`，`site: "淝水（寿阳）"`，可用 `site: '淝水'`。
   找不到对应事件也能做，只是没有浮签入口按钮，只能用 URL 打开。**不要为了挂载去改 `map_data.js`**，除非用户要求。
3. **定坐标**：所有坐标是 `[经度, 纬度]`（WGS84，十进制度）。古地名用今址坐标；可以参考 `map_data.js` / `lore_data.js` 里同名地点已有的 `coord`，保持一致。
4. **写数据**：按第 3 节的格式写进 `CAMPAIGNS`。
5. **更新资源版本号**：`node scripts/sync_version.js`（每次改完 JS/CSS 都要跑，否则浏览器加载旧文件）。
6. **逐阶段目测验证**：见第 5 节。
7. **跑校验**：`node scripts/sync_version.js --check` 和 `node scripts/validate_atlas.js`，两者都必须通过。

## 3. 数据格式

### 3.1 共享地点 `P` 与 `PLACE_NAMES`

```js
const P = {
  // 在这里加新地点，key 用小写拼音；不同战役共用同一张表，不要重名
  wulin: [113.54, 29.95],
};
const PLACE_NAMES = {
  wulin: { zh: '乌林', en: 'Wulin' },
};
```

`P` 只是给数据写起来方便的常量，阶段里的 `places` 数组引用的是这里的 key。也可以在箭头、壁垒里直接写坐标字面量。

需要复用的防线可以像 `FORT_DANHE` 那样提成常量，**命名加战役前缀**，比如 `FORT_CHIBI_WULIN`，避免和别的战役冲突。

### 3.2 战役条目

```js
const CAMPAIGNS = {
  changping: { ... },          // 已有
  chibi: {
    key: 'chibi',              // 必须和对象的 key 一致；也是 URL 里的 campaign=chibi
    zh: '赤壁之战',
    en: 'Battle of Red Cliffs',
    span: { zh: '208年 · 曹操 vs 孙刘联军', en: '208 CE · Cao Cao vs Sun–Liu' },
    yearRange: [207, 209],     // 闭区间；时间轴拖出这个范围会退出推演。必须包含所有阶段的 year
    match: { dynastyKey: 'donghan', year: 208, site: '赤壁' },  // 见第 2 步
    sides: [
      // 第 1 个阶营默认墨黑，第 2 个默认朱红；也可用 tone 指定
      { id: 'cao',  tone: 'ink',      zh: '曹军',     en: 'Cao Cao',     lead: { zh: '曹操 · 号称八十万', en: 'Cao Cao' } },
      { id: 'sunliu', tone: 'cinnabar', zh: '孙刘联军', en: 'Sun–Liu allies', lead: { zh: '周瑜、程普 · 刘备', en: 'Zhou Yu, Cheng Pu · Liu Bei' } },
    ],
    source: {
      zh: '据《三国志》……示意复原，路线与阵地位置为近似。',
      en: 'Schematic reconstruction after the Sanguozhi; routes and positions are approximate.',
    },
    phases: [ /* 见 3.3 */ ],
  },
};
```

阵营颜色 `tone` 可选值（定义在 `SIDE_PALETTE`）：`ink` 墨黑、`cinnabar` 朱红、`indigo` 靛蓝、`teal` 石绿、`ochre` 赭黄、`plum` 绛紫。也可以用 `color: '#xxxxxx'` 直接指定，但优先用调色板，和古舆图配色统一。两方颜色要对比明显；**进攻方 / 胜方不一定是黑色**，按阅读习惯选：通常把用户更关心的一方（或主角一方）设成朱红。

`id` 只用小写字母，阶段里所有 `side` 字段都引用它。

### 3.3 阶段 `phases[i]`

| 字段 | 必填 | 说明 |
|---|---|---|
| `year` | 是 | 这一阶段的年份（公元前用负数），切换时时间轴跳到这一年，底图疆域随之变化。必须在 `yearRange` 内 |
| `date` | 是 | `{ zh, en }`，面板上显示的时间，如 `'前260年 八月'` |
| `title` | 是 | `{ zh, en }`，阶段标题，8–14 个汉字为宜 |
| `view` | 是 | `[西经度, 南纬度, 东经度, 北纬度]`，相机要框住的范围。见第 4 节 |
| `text` | 是 | 阶段叙述，80–180 字。写成 `{ zh, en }` 才有英文；只写字符串则英文界面也显示中文 |
| `quote` | 否 | 史料原文摘录（只在中文界面显示），用中文引号 |
| `places` | 否 | `P` 里的 key 数组，画地名小圆点 + 名称 |
| `arrows` | 否 | 进军箭头，见下 |
| `forts` | 否 | 壁垒 / 防线，见下 |
| `areas` | 否 | 被围区域（椭圆），见下 |
| `units` | 否 | 主将旗标，见下 |
| `clashes` | 否 | 交战点（圈 ×），见下 |
| `cuts` | 否 | 交通线被切断标记（双斜杠），见下 |

**箭头 `arrows[j]`**

```js
{
  side: 'qin',                       // 阵营 id
  pts: [[108.7, 34.33], [110.87, 34.63], [112.93, 35.09]],  // ≥2 个点，从出发地到目的地；中间点决定弯曲走向，会被平滑成曲线
  label: { zh: '白起攻韩 · 取野王', en: 'Bai Qi seizes Yewang' },  // 可选，自动放在箭身中段外侧
  dashed: true,   // 可选：虚线空心箭头，表示非军事行动或意图（如「赵受上党」「佯败后撤」）
  heavy: true,    // 可选：粗箭头，表示主力 / 主攻方向
  light: true,    // 可选：细箭头，表示小股或多次突围
  blocked: true,  // 可选：箭头尖端画 ×，表示进攻受阻 / 突围失败
}
```

- 箭头按数组顺序依次「生长」，**先写先发生的**。
- 路线要沿真实可行的通道（河谷、关隘、渡口、陉道），不要直线穿越大山大河。中间点就是用来贴合地形的。
- 一个阶段 1–4 支箭头为宜，太多会乱。

**壁垒 `forts[j]`**

```js
{
  side: 'zhao',
  pts: [[112.9, 36.0], [112.915, 35.9], [112.93, 35.8]],  // 折线，按顺序
  face: -1,       // 齿朝哪边：1 = 沿 pts 方向的左侧，-1 = 右侧。应朝向敌方，画完看一眼，反了就取反
  label: { zh: '丹河壁垒', en: 'Dan River line' },  // 可选，标在第一个点附近
  lost: true,     // 可选：已失守（虚线、半透明）
  dim: true,      // 可选：背景参考（半透明），用于本阶段不是重点但需要保留位置的防线
}
```

**被围区域 `areas[j]`**

```js
{
  side: 'zhao',              // 被围的一方，决定填充色
  by: 'qin',                 // 可选：包围方，决定外圈虚线颜色；省略时取另一方
  center: [112.84, 35.81],
  rx: 0.05, ry: 0.055,       // 半径，单位是经度 / 纬度
  label: { zh: '赵军主力被围', en: 'Zhao main army trapped' },
  below: true,               // 可选：标签放在椭圆下方（默认上方），用来避让
}
```

**主将旗标 `units[j]`**：`{ side, at: [lng, lat], label: { zh: '白起', en: 'Bai Qi' } }`。放在部队所在处的**旁边**，不要压在地名、箭头上。

**交战点 `clashes[j]`**：`{ at: [lng, lat], label?: {zh, en} }`。

**断线标记 `cuts[j]`**：`{ at: [lng, lat], label: {zh, en} }`，标签画在标记下方。

## 4. 取景（`view`）怎么定

- `view` 是要完整看到的经纬度框，代码会自动预留右侧面板（桌面）或底部面板（手机）的位置，再留 12% 边距。
- 两种尺度：
  - **战略尺度**（双方调兵、千里奔袭）：框宽约 3.5–7 个经度。加上面板留白后屏幕可见宽度会超过约 4.6 个经度，底图上的城名、疆域、山河都会显示；
  - **战术尺度**（阵地、合围、突围）：框宽约 0.5–1 个经度。屏幕可见宽度小于约 4.6 个经度时会自动淡化地形、隐藏城名，只突出战役图形。放大有下限：屏幕最少显示约 0.85 个经度宽，框再小也按这个宽度显示。
- 一场战役通常前 1–2 个阶段用战略尺度交代来龙去脉，后面几个阶段用战术尺度。**相邻阶段 `view` 完全相同（数值一样）时相机不动**，只重画图形，阅读最连贯，所以战术阶段尽量共用同一个 `view`。
- 框要包住本阶段所有箭头、壁垒、旗标和它们的标签，四周再留一点余量。

## 5. 验证（必须做，不能只看代码）

本地服务固定用 **8000 端口**（项目根目录下 `./service.sh start` 启动的静态服务，直接读取工作区文件）。**不要另起其他端口的服务。** 如果 8000 没在运行，用 `./service.sh start` 启动。

1. 跑完 `node scripts/sync_version.js` 后，在浏览器打开
   `http://127.0.0.1:8000/?year=<第1阶段年份>&campaign=<key>&cphase=1`。
   这个 Python 静态服务不发送禁止缓存的响应头，**必须强制刷新**（`Cmd+Shift+R`，或者用 DevTools 的 reload ignoreCache），否则会拿到旧的 `index.html` 和旧脚本。可以在控制台执行 `[...document.scripts].map(s=>s.src).filter(s=>s.includes('campaign'))` 确认 `?v=` 是最新哈希。
2. **逐个阶段截图检查**，至少在两种窗口尺寸下（约 1440×900 和 1100×720）各看一遍：
   - 所有图形都在可见区域里，没有被右侧面板挡住；
   - 标签之间、标签和底图城名之间**没有重叠**（这是最常见的问题）；
   - 箭头方向、起止点符合史实，没有穿越不合理的地形；
   - 壁垒的齿朝向敌方；
   - 两方颜色和面板里的色块一致。
3. **交互检查**：
   - 在地图上点该战役的编年事件，浮签里有「⚔ 战役推演 ›」按钮，点击能进入（前提是 `match` 写对了）；
   - 「上一步」「下一步」、阶段编号按钮都能切换；「自动播放」点下立即前进一步，之后每 6 秒前进一步，到最后一步停止；
   - Esc 或 × 能退出；拖动时间轴离开 `yearRange` 也会退出；
   - 切换英文（`&lang=en`），检查英文标签长度没有造成新的重叠。
4. 控制台除了 `cloudflareinsights` 统计脚本的跨域报错（本地环境固有，与功能无关），不应有其他错误。
5. 跑 `node scripts/sync_version.js --check` 和 `node scripts/validate_atlas.js`。

常见问题处理：

| 现象 | 处理 |
|---|---|
| 标签重叠 | 调整箭头中间点让标签换位置；把旗标挪开；去掉与底图城名重复的 `places`；被围区域用 `below: true`；缩短标签文字 |
| 底图城名和自己画的地名重复 | 战略尺度下底图已显示主要城市，`places` 只放底图上**没有**的地点（陉道、关隘、营垒等） |
| 图形被面板挡住 / 太小 | 收紧或调整 `view` |
| 壁垒齿朝向反了 | `face` 取反 |
| 改了没效果 | 没跑 `sync_version.js`，或浏览器没强制刷新 |

## 6. 内容写作规范

- 叙述用简洁的书面语，先写「谁、做了什么、结果」，再补原因。每阶段一个核心事件。
- 人名、地名、官职与 `lore_data.js` / `map_data.js` 已有写法保持一致（例如「白起」「王龁」「武安君」）。古地名第一次出现时用括号注今地，如「野王（今河南沁阳）」。
- `quote` 必须是史料原文，不要自己编；拿不准就不写。
- 兵力、伤亡等数字按史料原文说法（「号称」「约」），不要自己推算。
- 有争议的地点或路线，取主流说法，并在 `source` 里写明是示意复原。
- 英文写简短的意译，不要逐字直译。

## 7. 需要改代码的情况（先问用户）

下列需求超出了当前数据格式，**先和用户确认再动渲染代码**：

- 三方及以上的阵营（颜色能配，但被围区域的外圈默认取「另一方」，需要用 `by` 显式指定）；
- 水战船队、火攻、水淹等需要专门图标的效果；
- 海上航线、跨越地图边界（经度 66–142、纬度 14–55 以外）的战役；
- 一个阶段需要显示多个年份的疆域。

改了渲染代码后，必须重新验证长平之战的 7 个阶段没有被改坏。
